[Docker] 이미지 생성 및 관리 기술의 4단계 진화 과정

[1단계] commit ──> [2단계] build ──> [3단계] buildx ──> [4단계] compose
(수동 스냅샷)       (설계도 자동화)     (멀티 아키텍처)      (다중 컨테이너 빌드)

1단계: docker commit (수동 스냅샷 방식)
	
	개념: 
		실행 중인 컨테이너의 현재 상태를 그대로 사진 찍듯 이미지로 저장합니다.
	한계: 
		편리하지만 이미지 내부가 어떻게 구성되었는지 알 수 없고(블랙박스화), 자동화가 불가능합니다.
	용도: 
		임시 백업, 가벼운 실험용 데이터 보존.

2단계: docker build (Dockerfile 설계도 방식)
	
	개념: 
		Dockerfile이라는 텍스트 파일에 인프라 구축 과정을 코드로 기록하고, 
		이를 기반으로 이미지를 자동 빌드합니다.
	발전: 
		인프라의 자산화(IaC)가 가능해져 배포 자동화의 기반이 되었습니다.
	용도: 
		단일 컨테이너 기반 애플리케이션의 정식 이미지 제작.

3단계: docker buildx (크로스 플랫폼 및 성능 확장 방식)
	
	개념: 
		기본 build 기능을 확장한 차세대 빌드 도구입니다 (도커 내장 플러그인).
	발전:
		멀티 아키텍처 빌드: 내가 인텔/AMD(x86) PC에서 빌드를 해도, 
		맥북(M1/M2/M3 등 ARM)이나 라즈베리 파이에서 돌아가는 이미지를 동시에 만들어낼 수 있습니다.
		강력한 캐싱: 빌드 속도가 획기적으로 빨라집니다.
	용도: 
		글로벌 서비스 배포, 다양한 서버 환경을 고려한 멀티 플랫폼 이미지 제작.

4단계: docker compose (build) (다중 컨테이너 및 인프라 통합 방식)
	
	개념: 
		docker-compose.yml 파일 안에 여러 개의 Dockerfile 빌드 경로를 지정하여, 
		연동된 수많은 컨테이너의 이미지를 단 한 줄의 명령어로 일괄 빌드 및 실행합니다.
		
	발전: 
		단일 이미지 생성을 넘어 웹 서버, DB, 캐시 등이 얽힌 전체 애플리케이션 
		인프라 환경을 통째로 빌드하고 관리합니다.
		
	용도: 마이크로서비스 아키텍처(MSA) 개발 환경, 복잡한 다중 컨테이너 시스템 구축.

-------------------
💡 한 줄 요약 맵핑

commit: 지금 상태 대충 백업할 때
build: 제대로 된 설계도 기반 정식 이미지를 만들 때
buildx: 다양한 CPU 환경(Intel, ARM 등)에 맞는 이미지를 한 번에 구워낼 때
compose: 여러 컨테이너 설계도를 묶어서 한 번에 빌드하고 실행할 때
