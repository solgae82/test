1. Gunicorn의 정체

	WSGI(위스기) 웹 서버 쉽게 말해, 
	"파이썬 웹 앱(Flask, Django 등)을 실제 인터넷 세상에 안전하고 빠르게 서비스할 수 있도록 
	감싸주는 실무용 웹 서버 엔진"입니다.

		이름의 유래: Green Unicorn(초록 유니콘)의 약자입니다.

2. 왜 Flask (app.run())를 그냥 쓰면 안 되고, Gunicorn을 써야 하나요?

	server.py 마지막에 있던 app.run(host='0.0.0.0')은 "개발자 로컬 테스트용" 간이 서버입니다. 
	실무 배포 환경에 그냥 쓰면 대형 사고가 납니다.

	Flask 내장 서버 (app.run):
		싱글 스레드(Single Thread) 방식입니다.
		쉽게 말해, 가게에 직원이 딱 1명 있는 겁니다. 
		손님 A가 접속해서 무거운 데이터를 다운받느라 5초 동안 머물면, 
		손님 B와 손님 C는 접속도 못 하고 5초 동안 멍하니 대기해야 합니다. (동시 접속 처리 불가)
	
	Gunicorn 서버:
		멀티 프로세스(Multi-Process, 워커) 방식입니다.
		가게에 직원(Worker)을 여러 명 둡니다. 
		아까 보신 gunicorn --workers=9가 바로 "컴퓨터 안에 직원 9명을 대기시켜라"라는 뜻입니다. 
		손님 9명이 동시에 접속해도 대기 없이 9명의 직원이 각각 1초 만에 칼답변을 보내줍니다.
	
3. 실무 아키텍처에서의 Gunicorn 역할 (3줄 요약)

	도커 컨테이너가 실행될 때(CMD), Gunicorn은 내부에서 다음과 같은 우주 방어 역할을 합니다.
	
	1) 동시 접속 차단 방지: 
		여러 명의 사용자가 동시에 접속해도 요청을 부드럽게 분산 처리(로드밸런싱)합니다.
	2) 프로세스 자동 관리 (좀비 방지): 
		만약 3번 직원(Worker) 프로세스가 일하다가 에러가 나서 뻗어버리면, 
		대장 Gunicorn(Master)이 이를 감지하고 초시속으로 새로운 직원 프로세스를 즉시 살려내어 
		서버가 멈추지 않게 방어합니다.
	3) 보안 및 안정성: 
		해킹 공격이나 비정상적인 대용량 요청이 들어왔을 때, 
		Flask 코드가 직접 맞지 않도록 전면에서 1차 차단벽 역할을 해줍니다.
		
💡 최종 개념 매칭
	Flask (server.py): 
		요리사 (맛있는 웹 화면과 데이터를 만들어내는 로직)
		
	Gunicorn: 
		서빙 직원들 (손님들이 몰려올 때 줄 세우고, 서빙하고, 가게가 터지지 않게 관리하는 인력들)
		그래서 실전 Dockerfile 마지막 줄에 python server.py가 아니라, 
		gunicorn server:app을 적어두셨던 것입니다!		
		
		
------------------- 실전 연습 하다가 만난 오류

Gunicorn 멀티 워커의 비밀 (오류 원인과 대책)
 
	# 1개 프로세스로 실행 (로컬/테스트 환경용)
	# --workers 옵션 없으면 기본 --workers=1
	 
	CMD ["gunicorn", "--workers=1", "--bind", "0.0.0.0:5000", "server:app"]

	# 9개 프로세스로 실행 (실무 운영 환경용 - 보통 CPU 코어 수 * 2 + 1개 설정)
	CMD ["gunicorn", "--workers=9", "--bind", "0.0.0.0:5000", "server:app"]

❓ 왜 워커가 여러 개일 때 에러(예상치 못한 오류)가 날까요?

	Flask 기본 내장 서버나 싱글 워커(--workers=1) 환경에서는 
	모든 사용자의 요청을 단 하나의 프로세스가 처리하므로, 
	메모리(전역 변수, 파이썬 세션 등)에 로그인 정보나 데이터를 저장해도
	유실되지 않고 똑같이 유지됩니다.

	하지만 --workers=9를 주면 독립된 파이썬 프로세스 9개가 동시에 실행됩니다.
	
	1. 첫 번째 요청(로그인)은 1번 워커 프로세스가 받아서 자기 메모리에 로그인 성공 정보를 저장했습니다.
	
	2. 새로고침을 눌러 발생한 두 번째 요청은 도커/Gunicorn 로드밸런싱에 의해 5번 워커 프로세스로 갈 수 있습니다.
	
	3. 5번 워커 프로세스 메모리에는 로그인 정보가 없으므로 사용자는 로그인이 풀리는 세션 불일치 오류를 겪게 됩니다.
	
🛠️ 실무 해결책 (상태 비저장성 - Stateless 아키텍처)

	이 문제를 해결하려면 멀티 워커 컨테이너 내부 메모리에 데이터를 저장하면 안 됩니다.

	세션/상태 저장: 
		파이썬 가상 메모리가 아닌 외부 데이터베이스(DB)나 
		고속 인메모리 시스템인 Redis를 세션 스토어로 활용합니다.

	인증 분리: 
		서버가 상태를 기억하지 않아도 되는 JWT(Json Web Token) 방식을 채택하여 
		클라이언트가 토큰을 들고 다니게 만듭니다. (이 방식이 파이썬 생태계의 실무 표준입니다.)
