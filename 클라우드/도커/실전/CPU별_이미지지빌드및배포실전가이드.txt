[Docker] CPU 아키텍처별 이미지 빌드 및 배포 실전 가이드

도커의 "Build Once, Run Anywhere"는 CPU 아키텍처(amd64, arm64 등)가 같을 때만 유효합니다. 
아키텍처가 다르다면 빌드 방식을 분리해야 합니다.

	    ┌───> [케이스 1] CPU 아키텍처가 같을 때 ──> 일반 `build` (또는 `commit`)
[배포 환경 기준]┤
            └───> [케이스 2] CPU 아키텍처가 다를 때 ──> `buildx build` (QEMU 에뮬레이션)
		

--------- 케이스 1. 빌드 환경과 배포 환경의 CPU 아키텍처가 같을 때

상황: 로컬 PC(Intel/AMD) ➡️ 운영 서버(Intel/AMD 리눅스)
	
	
1) Docker Hub 이용 패턴 (추천)

	# 1. 이미지 빌드 (추천) 또는 커밋 (비추천)
	docker build -t solgae/my-flask-app:1.0 .
	# docker commit -m "flask app" -a "dong" my-flask-app solgae/my-flask-app:1.0

	# 2. 도커 허브 업로드
	docker login
	docker push solgae/my-flask-app:1.0

	# 3. 배포 서버에서 다운로드
	docker pull solgae/my-flask-app:1.0

2) 폐쇄망 인프라 패턴 (파일 전송)

	# 1. 로컬 PC: 이미지 파일 압축 저장
	docker save -o flask-app.tar my-flask-app:1.0

	# 2. 배포 서버: tar 파일 전송 후 이미지 복원
	docker load -i flask-app.tar

3) 현지 빌드 패턴

	배포 서버에 소스 코드와 Dockerfile을 직접 전송한 뒤 서버에서
		docker build -t app . 
	
	실행

--------- 케이스 2. 빌드 환경과 배포 환경의 CPU 아키텍처가 다를 때

상황: 로컬 PC(Intel/AMD amd64) ➡️ 운영 서버(M 시리즈 맥 또는 AWS Graviton arm64)

	※ arm64 전용으로 빌드된 이미지는 빌드한 amd64 PC 도커에서 실행할 수 없습니다.	

1) Docker Hub 이용 패턴 (멀티 플랫폼)

	buildx는 에뮬레이터(QEMU)를 사용하므로 빌드 속도는 저하되지만, 
	이종 아키텍처 이미지를 구워낼 수 있습니다. 

	뒤에 --push를 붙여 도커 허브로 바로 전송합니다.

	(예제)
	# 방법 A: 두 아키텍처를 모두 지원하는 '멀티 플랫폼 단일 태그' 이미지 빌드 및 푸시
	docker buildx build --platform linux/amd64,linux/arm64 -t solgae/multi-flask-app:1.0 --push .

	# 방법 B: 타깃 서버(arm64) 전용 이미지 빌드 및 푸시
	docker buildx build --platform linux/arm64 -t solgae/flask-app:linux-1.0 --push .

	# [배포 서버] 다운로드 (도커가 서버 CPU에 맞는 레이어를 자동으로 식별하여 다운로드함)
	docker pull solgae/multi-flask-app:1.0

2) 폐쇄망 인프라 패턴 (파일 전송)

	buildx 결과물은 로컬 도커 엔진이 인식하지 못하므로, 
	--load 옵션을 주어 로컬 이미지 리스트로 강제 인출한 뒤 패키징해야 합니다.
	
	(예제)
	# 1. 로컬 PC: 타깃 아키텍처 빌드 후 로컬 엔진으로 인출
	docker buildx build --platform linux/arm64 -t solgae82/flask-app:linux-1.0 --load .

	# 2. 로컬 PC: 압축 파일 생성
	docker save -o flask-app.tar solgae82/flask-app:linux-1.0

	# 3. 배포 서버: tar 파일 전송 후 이미지 복원
	docker load -i flask-app.tar

3) 현지 빌드 패턴 (실무 강력 추천)
	
	크로스 빌드 오버헤드(성능 저하)를 피하기 위한 가장 깔끔한 방법입니다.
	
	배포 대상 서버(arm64)로 소스 코드와 Dockerfile을 옮긴 뒤, 
	해당 서버에서 docker build를 수행하면 가상 에뮬레이션 없이 
	해당 CPU에 최적화된 이미지가 즉시 빌드됩니다.

--------- 💡 핵심 요약 가이드

인터넷이 된다면: 
	buildx ... --push를 사용하여 Docker Hub를 매개체로 배포하는 것이 가장 간편합니다.
	
폐쇄망 환경이라면: 
	buildx ... --load 처리 후 docker save/load 스크립트를 구성합니다.
	
가장 속도가 빠른 방법: 
	다른 거 신경 쓰지 않고 배포될 실제 서버에 소스를 올려서 직접 build 치는 것이 
	에뮬레이터(buildx)를 돌리는 것보다 압축/컴파일 속도가 훨씬 빠릅니다.
