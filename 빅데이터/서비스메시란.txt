💡 서비스 메시란?

"네트워크 스택을 한 번 더 감싸서, 
애플리케이션 코딩 없이 인프라 수준에서 보안과 제어 능력을 주입하는 기술"

기존에 개발자가 코드에 일일이 구현하던 통신·보안·모니터링 기능을 
인프라(프록시)가 컨테이너 레벨에서 알아서 투명하게 감싸서 대행해 주는 것, 
 
기존의 TCP/IP 같은 네트워크 레벨(기존 통신 스택) 위를 
마치 실리콘 케이스처럼 한 겹 더 감싸서(Wrapping), 
알맹이인 애플리케이션 코드는 건드리지 않고도 
보안, 모니터링, 트래픽 제어 같은 고성능 기능들을 공짜로 얻는 기술

주로 동기 통신에 적용한다.
-------------------
<기존 통신방식과 서비스 메시 통신 방식 차이>

1. 기존 방식 (애플리케이션 내부에서 처리)

	예전에는 타임아웃, 재시도, 암호화, 호출 추적 같은 기능을 구현하려면 
	개발자가 직접 코드나 라이브러리(예: Spring Cloud, Netflix OSS)로 
	애플리케이션을 감싸야(Wrap) 했습니다.

	• 단점: 자바, 파이썬, 고(Go) 등 언어가 바뀔 때마다 
	똑같은 통신 코드를 새로 짜거나 다른 라이브러리를 써야 했습니다.

2. 서비스 메시 방식 (인프라 수준에서 감싸기)

	서비스 메시는 애플리케이션 코드에는 일절 손을 대지 않습니다. 
	대신 컨테이너(Pod) 네트워크 안에서 
	애플리케이션 바로 옆에 경량 프록시(Envoy 등)를 두고, 
	밖으로 나가는 모든 통신을 이 프록시가 가로채서(Wrap) 대신 처리합니다.

	• 동작 예시:
	1. A 서비스가 그냥 평범하게 http://service-b로 호출을 보냅니다.
	2. A 바로 옆에 붙어 있는 서비스 메시 래퍼(프록시)가 이 요청을 낚아챕니다.
	3. 이 래퍼가 상대방(B)의 위치를 찾고(Service Discovery), 
	통신을 암호화(mTLS)하고, 실패하면 알아서 다시 시도(Retry)한 뒤 
	B 서비스의 래퍼에게 안전하게 전달합니다.

-------------------
<서비스 메시를 쓰는 상황 (동기 통신)>

	비동기에도 적용 가능하나, 편리 기능을 쓰기 위해서 동기 통신에 적용하는게 기본.
	
	• 실시간 응답이 필요할 때: 
		유저가 로그인 버튼을 눌러 "인증 서비스"가 "회원 데이터 서비스"에 
		즉시 확인을 요청해야 하는 상황.

	• 네트워크 제어가 필요할 때: 
		"A 서비스가 B 서비스로 보내는 트래픽의 10%만 신버전(Canary)으로 보내고 싶다"거나 
		"두 서비스 간 통신을 암호화(mTLS)하고 싶다"는 요구가 있을 때.

-------------------
<기술 특징>

핵심 역할:	서비스 간 직접 통신(호출) 관리 및 보안
통신 방식:	동기식 (Synchronous) 통신 (주로 HTTP, gRPC)
주요 비유:	통화 연결 및 도청 방지 (전화망)
데이터 저장:	데이터를 저장하지 않음 (전달 즉시 소멸)
장애 대응:	상대가 일시 오류면 재시도(Retry), 먹통이면 차단(서킷 브레이커)
대표 기술:	Istio, Linkerd

------------------
<얻는 이점>

🛡️ 1. "보안 강화"를 공짜로

	기존에는 서비스 간 통신을 암호화하려면 소스코드에 TLS 인증서를 심고 난리를 쳐야 했습니다. 
	이제는 서비스 메시라는 래퍼가 네트워크 통신 스택을 감싸고 있으니, 
	자기들끼리 알아서 암호화(mTLS)하고 인증서도 주기적으로 알아서 갱신합니다. 
	내부 코드는 그냥 평문(HTTP)으로 쏴도 밖으로 나갈 땐 최고 등급 보안 카드로 무장하게 됩니다.

📊 2. "전체 통신 모니터링"을 공짜로

	"누가 누구를 호출했는지", "어디서 병목이 생겨서 느려지는지" 알려면 
	예전에는 코드마다 로그를 심어야 했습니다. 
	
	하지만 네트워크 스택이 감싸여 있으니, 
	이 래퍼가 지나가는 모든 트래픽의 통계를 지켜보며 
		"
		어라, A가 B 호출할 때 0.5초 걸리네?" 하고 
	
	대시보드(Grafana, Kiali 등)에 예쁜 그래프로 다 그려줍니다.

🚦 3. "지능형 트래픽 제어"를 공짜로

	새로운 버전(V2)의 서비스를 배포할 때, 
	"불안하니까 전체 트래픽 중 딱 5%만 V2로 흘려보내고, 
	나머지는 기존 V1으로 보내자" 같은 정교한 제어가 가능해집니다. 
	
	이 역시 코드를 고치는 게 아니라, 네트워크 레벨의 래퍼(프록시)한테 
	"너 지금부터 신형 도로로 5%만 차 보내"라고 명령만 내리면 끝나는 일입니다.
	
-------------------
<플러그인 처럼 추가/제거가 가능>

애플리케이션 소스코드를 단 한 줄도 고치지 않기 때문에, 
처음부터 무리해서 넣을 필요 없이 시스템이 커지고 필요성이 느껴질 때 
나중에 덧붙이거나(Plug-in), 
쓰다가 마음에 안 들면 언제든지 제거(Plug-out)할 수 있습니다.

이를 인프라 진영에서는 "애플리케이션에 투명하다(Transparent)"고 표현합니다.
실제로 적용하고 제거하는 과정도 매우 직관적입니다.

➕ 나중에 덧붙일 때 (추가)

	1. 서비스 메시 인프라 설치: 
		
		쿠버네티스(Kubernetes) 같은 환경에 
		서비스 메시(예: Istio) 시스템을 먼저 설치합니다.

	2. 스위치 켜기 (네임스페이스 라벨링): 
		
		"이제부터 이 구역의 서비스들은 서비스 메시를 적용하겠다"고 
		시스템에 선언(라벨 지정)합니다.

	3. 재시작: 
		
		실행 중인 애플리케이션을 한 번 재시작(Rolling Restart)해 줍니다.
		
		• 이때 쿠버네티스가 애플리케이션이 뜰 때 
		옆방에 네트워크 래퍼(사이드카 프록시)를 자동으로 슥 끼워 넣습니다.
		
		• 이제부터 보안(mTLS), 모니터링 기능이 즉시 활성화됩니다.

➖ 필요 없어서 뺄 때 (제거)

	1. 스위치 끄기: 적용했던 구역의 선언(라벨)을 해제합니다.
	
	2. 재시작: 서비스를 다시 한번 재시작합니다.
		
		• 쿠버네티스가 이번에는 옆방에 있던 네트워크 래퍼를 쏙 빼고 
		애플리케이션만 깔끔하게 띄웁니다.
		
		• 시스템은 예전의 순수한 일반 통신 상태로 완벽하게 돌아갑니다.

⚠️ 다만, 실무에서 고려해야 할 '사소한 주의점' 딱 두 가지

	이론적으로는 완전히 뗐다 붙였다 할 수 있지만, 
	실제 운영 환경에서는 다음 두 가지를 인지하고 계시면 좋습니다.

	• 네트워크 경로 변경에 따른 점검: 
		
		래퍼를 붙이거나 뗄 때 통신 경로(라우팅)가 미세하게 바뀝니다. 
		
		따라서 제거하거나 추가한 직후에 
		"혹시 네트워크 방화벽이나 타임아웃 설정 때문에 통신이 끊기는 곳은 없는지" 
		가볍게 검증(스테이징 환경 테스트)은 필요합니다.
	
	• 약간의 자원(CPU/메모리) 소모: 
		
		애플리케이션마다 옆에 래퍼(프록시)가 하나씩 더 붙기 때문에, 
		서버의 메모리와 CPU를 조금씩 더 나눠 쓰게 됩니다. 
		
		뗐다 붙였다 할 때 서버 자원 여유가 있는지는 체크해야 합니다.
